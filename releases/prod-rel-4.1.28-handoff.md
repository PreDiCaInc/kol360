# prod-rel-4.1.28 — Handoff to Prod Team

**Status:** Ready for prod deploy. **No migrations.** Reversible.
**Tag:** `prod-rel-4.1.28` → commit on `main` (cut immediately after this PR merges).
**Supersedes:** `prod-rel-4.1.27` (v1.17.47).
**Bundles:** v1.17.48 — single backend change: branded SES invitation email replaces Cognito's default one-line message.

## TL;DR

Pteam: *"the email that went out with user invite is really poor quality... also the email doesn't have a link to where they need to go — its a one line username and temp password."*

Replaced Cognito's default invite email with a polished SES template that matches the survey-invitation aesthetic, includes a sign-in CTA button, and explains the temp password's lifecycle.

## What changes for customers

| Surface | Before (4.1.27) | After (4.1.28) |
|---|---|---|
| New-user invitation email | Cognito default: plain text, one line of credentials, no branding, **no link to the app**, no instructions | New polished SES template: gradient header w/ KOL360 logo, "Welcome, {name}", optional client-context line, code-style credentials block (username + temp password in monospace), **"Sign In to KOL360" CTA button** linking to `${APP_URL}/login`, role label, fallback copyable link, security note ("don't share, one-time use, expires on first sign-in"), branded footer. Plain-text fallback included. |
| Temp password origin | Cognito generated it on `adminCreateUser` (no `TemporaryPassword` was passed) | API generates it locally with `crypto.randomBytes` (16 base64-ish chars + a symbol + `Aa1` suffix → guarantees all four Cognito password-policy character classes). Passed to `adminCreateUser` with `MessageAction='SUPPRESS'` so Cognito no longer sends anything. |
| Failure behavior | One step (Cognito sends or fails) | If SES send fails after Cognito + DB success, we log the error and return the new user. Admin can resend via the existing resend path. No state rollback. |

## Migrations

**None.** Code-only.

## Risk

**Low-medium.** Real behavior change to the invite flow but:
- The two operations either side of the email send (Cognito user creation + DB User row insert) are unchanged.
- The new email goes through the SAME `sendEmail()` helper used for the survey invites — same SES configuration set, same delivery-event tracking (v1.17.37).
- Cognito user is still created with status `PENDING_VERIFICATION` and a temp password; the user goes through the same first-sign-in NEW_PASSWORD_REQUIRED challenge flow. No client-side / login change needed.

What to watch for:
- The temp password is now generated by the app, not Cognito. The format meets the Cognito user-pool password policy (8+ chars, all four character classes) but if pteam ever tightens that policy, the generator needs to match.
- The SES from address (`research@bio-exec.com`) is the same one used for survey invites; ensure invitation deliverability isn't affected by any new sender-reputation patterns.
